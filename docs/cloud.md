# AutoSave in synced cloud folders, and version history

> **Last reviewed:** 2026-11-09 · **Last updated:** 2026-11-09 · **Change:** Version History pane, title bar file menu and read only previous versions with Compare, Restore, Save a copy and Close · **Target:** Microsoft PowerPoint (Microsoft 365) for Windows

DeckCraft uses the desktop sync clients' ordinary folders. It does not connect to a cloud API. A file saved in one of these folders is uploaded by the installed client and becomes available on the person's other devices.

## Folder discovery

On macOS, DeckCraft checks `~/Library/Mobile Documents/com~apple~CloudDocs` for iCloud Drive, each `GoogleDrive-<account>` and `OneDrive-<account>` under `~/Library/CloudStorage`, then the older `~/Google Drive` and `~/OneDrive` folders. On Windows, iCloud Drive is `%USERPROFILE%\iCloudDrive`. Google Drive may be a drive letter whose root contains `My Drive`, or a mirrored `%USERPROFILE%\My Drive`. OneDrive uses `%OneDriveConsumer%`, `%OneDriveCommercial%` or `%OneDrive%`. On Linux and other systems there is no assumed client path; `DECKCRAFT_CLOUD_ICLOUD`, `DECKCRAFT_CLOUD_GDRIVE` and `DECKCRAFT_CLOUD_ONEDRIVE` can name folders. The browser build has no folders to discover.

The desktop host discovers the roots once, off the UI thread. `file.cloud={}` reports provider, root, current path, conflict state and the discovered roots. Provider ids are `icloud`, `gdrive` and `onedrive`. iCloud-only files must be downloaded by the sync client before opening.

## Save a new presentation

Turning AutoSave on for a presentation that was never saved opens the Save to Cloud dialog, which asks where AutoSave should keep it. With no cloud folder known it opens Save As instead. `file.saveToCloud` accepts optional `provider` (`icloud`, `gdrive` or `onedrive`), `root` (one of the folders `file.cloud` lists, for an account other than the first) and `name` (without extension). With no provider, the first discovered root is chosen in iCloud Drive, Google Drive, OneDrive order. The file is written as a new `.pptx` in that provider's folder, with a numbered name when needed.

This is the same basic model PowerPoint uses when a new presentation is saved to OneDrive: the application chooses a synced location and the sync client handles the upload. DeckCraft does not provide Microsoft's service integration or coauthoring.

## Conflict protection

DeckCraft keeps a disk stamp for each presentation's file: its size, its modification time and a fast byte digest, taken when the file is read or written here. AutoSave calls `file.save` with `ifUnchanged`. If another device or program changed the bytes, or the file is missing because it was moved or deleted, AutoSave does not overwrite it. It records `changed` or `missing` and pauses. A timestamp-only touch with identical bytes is accepted.

The Save Conflict dialog offers **Keep both**, **Keep this version**, **Open the other version**, **Decide later** and **Save it here again**. `file.resolveConflict` takes `{"keep":"both"}`, `{"keep":"mine"}` or `{"keep":"theirs"}`. `both` writes `Name (conflict copy).pptx` beside the other version and edits the copy. `mine` overwrites the path. `theirs` reopens the file on disk and cannot reopen a missing file. When the file is missing, the dialog offers only **Save it here again** (`mine`, which writes the presentation back to its original path) and **Decide later**.

## Closing and switching presentations

With AutoSave on, an edited presentation closes, or the app quits, after DeckCraft writes the pending changes with `file.save` and `{"ifUnchanged":true}`. The action continues without a Save Changes prompt. If another device changed the file, the Save Conflict dialog opens and the presentation stays open. If Save Changes was already visible, a successful AutoSave closes that prompt and continues the pending action. With AutoSave off, the Save Changes prompt stays.

## AutoSave for each file

AutoSave is on by default for every presentation whose file exists on disk in a format that keeps everything (`.deckcraft`, `.pptx`, `.potx` and `.ppsx`). That covers local files as well as files in iCloud Drive, Google Drive or OneDrive folders, and an opened file is covered at once, without a save first. PowerPoint turns AutoSave on by default only for files stored in OneDrive or SharePoint. DeckCraft also covers local files because the project owner decided so. The disk stamp read when the file is opened protects a local file in the same way as a cloud file.

The switch in the title bar is off, with the reason in its tooltip, for a new presentation that has never been saved, a previous version opened from the history (it has no file), a format that does not keep everything, the browser, and a file with a conflict waiting. A file opened from bytes, or a recovered presentation, needs an explicit save before AutoSave writes it, because DeckCraft has no disk stamp to check first.

A write that fails, for example because another program holds the file, does not turn AutoSave off. AutoSave pauses and tries again after 5 seconds, then waits twice as long after each further failure, up to one minute. The status bar shows the error while writes keep failing, and the message goes away after the next successful write.

Each file remembers its switch, as PowerPoint remembers it for each presentation. Turning AutoSave off for a file is remembered when it is opened again, including in later runs; turning it back on forgets the choice. The choices are kept in `<settings_dir>/autosave.json`, never in the presentation, so remembering one does not change the file's bytes. Paths are normalized: on Windows the `\\?\` prefix of canonical paths is removed, separators become `\` and letter case is ignored, and letter case is also ignored on macOS. The file keeps at most 2000 entries, drops the oldest first, is read only up to 1 MiB and is written atomically through a temporary file. Renaming a file (`file.rename`) keeps its choice. Save As, Save to Cloud and Keep both give the new file the switch the presentation had.

Preferences › Saving › **Turn on AutoSave by default** sets the default for files with no choice of their own. `file.autosave` with `{"value": bool}` (or `{}` to toggle) sets the open presentation's switch and remembers it for the file, exactly as the title bar switch does. To read the state without changing it, use `file.cloud={}`: its `autosave` object has `on`, `default`, `remembered`, and in the app `covers` and `blocked`.

File › Home and Open list each file once in Recent, using the same path rules without reading the disk. On Windows, `C:\Docs\A.pptx` and `c:/docs/a.pptx` are one entry.

## Version history

The desktop app keeps a local history for each saved presentation. By default it is in `<settings_dir>/versions/`, in one folder per presentation. A `.pptx`, `.potx` or `.ppsx` package is filed under its document id; any other format (`.deckcraft`) is filed under a hash of its canonical path. Each version is described by its own file: the manifest of a version kept as parts, or `<id>.meta.json` beside a whole copy `<id>.bin`. The description gives `id`, `savedAt` (UTC), `author`, `size`, `kind`, `windowStart`, `digest` (SHA-256 of the saved bytes), `session`, `capturedAt`, `storage` (`whole` or `parts`), `stored` (the disk space the version added), `supersedes`, `documentId` and `details` (below). Every file the history writes is flushed and read back before it replaces anything, and the history folders are created private to the user (mode 0700 on Unix). History is written in the background by a worker. A failure in the history is reported and logged; it never stops a save and never changes the bytes saved. Only the presentation's own file has a history: a copy exported in another format, such as PDF or an outline, does not create one.

Every explicit save creates a version. PowerPoint's AutoSave on OneDrive adds a version at the first change after a presentation opens and then about every ten minutes. DeckCraft does the same: the first AutoSave write of each editing session (one opening of the presentation) starts a new version, and later writes from that session update it until ten minutes have passed since the version was started. The last write before the presentation closes is therefore always in the history.

Before any save writes over a file whose current bytes are not already in its history, DeckCraft stores those bytes byte for byte, synchronously, before the file is replaced. The version is `original` when the presentation had no history yet, and `external` when another program or computer changed a file that already had one. `savedAt` is then the file's modification time.

A `.pptx` is a zip archive whose parts are compressed separately, so a one-letter edit changes most of the file's bytes. The history therefore opens the archive and keeps each part as an object in `objects/`, named by the SHA-256 of its content. A picture, font or theme part that did not change between saves is stored once. A part that changed is stored as a compressed delta against the same part of the previous version, and after ten deltas in a row, or when a delta would be more than half the size of the compressed part, the part is stored whole again. Each version kept this way is a manifest, `<id>.parts.json`, that lists the parts in archive order. Opening, restoring or saving a copy rebuilds the archive from the manifest, and every part is checked against its hash. The rebuilt zip can differ from the saved file in its compressed bytes, but each part has the same content. The `original` version and any file that is not a zip, or that exceeds the limits (10,000 parts, 256 MiB for a part, 1 GiB uncompressed in total), is kept byte for byte. The limits are checked against the sizes the archive declares and every read is capped at the declared size, so a zip bomb is stored whole and never inflated.

Retention follows the automatic version limits of SharePoint and OneDrive for work. All versions are kept for 30 days. From 30 to 60 days, the newest version of each hour is kept. From 60 to 180 days, the newest of each day is kept. After that, the newest of each week is kept. Age alone never empties a history. Each presentation keeps at most 500 versions and 500 MiB of real disk space, newest first, with a part shared by several versions counted once. Objects that no kept version needs are deleted after pruning, and if any manifest or object header cannot be read, nothing is deleted on that pass. The oldest `original` version is pinned. A version whose bytes no longer match its digest is refused.

Each package gets a random document id, a UUID version 4 that is derived from nothing: not the computer, the user, the time or the path. It is stored in `docProps/custom.xml` as the custom property `DeckCraftDocumentId`. PowerPoint keeps custom properties when it saves, so the id survives a round trip through it. The id is assigned at the presentation's first save, whether it was created in DeckCraft or received from someone else. The history follows the id, so a file renamed or moved, inside or outside the app, keeps its history, as OneDrive keeps a file's history through a rename or move.

Save As, Save to Cloud, Keep both and Save a copy of a version write a new file. It gets a new id, and its first version, of kind `saveAs` or `conflictCopy`, records the presentation and version it came from in `details.origin`. The original file keeps its own history. A copy made outside the app, such as two files carrying the same id while the one the history last saw still exists, gets a new id at its next save and records its origin the same way (`trigger` is `copy`). A `.deckcraft` file carries no id, so its history is kept by path; it follows `file.rename` and is found again after a move outside the app when its newest version holds exactly the bytes now in the file.

The history can be kept in one or two folders (Preferences › Saving › Version history; `file.options` `versionsFolder` and `versionsMirror`). The default is the settings folder alone. Another folder can replace it, or both can be used as mirrors. Every write goes to every folder that can be reached, and listing and reading use all of them. A folder that cannot be reached does not stop the save; it is reported in `versionsUnavailable` and brought up to date when it is back. When the folders change, the history already kept is copied, moved or left in place (`versionsExisting`: `copy`, the default, `move` or `leave`). A history folder can be one that a cloud app syncs between two computers, because nothing in it is ever rewritten: each version is an immutable file with a random name, objects are named by their content, there is no shared index, and an unneeded object is deleted only after it has stayed unneeded for 7 days. A history folder inside iCloud Drive, OneDrive or Google Drive is as private as that account.

`file.versions={}` lists versions newest first: `{id,savedAt,author,size,stored,kind}` and also `storage`, `documentId`, `supersedes` and `details`. `kind` is `save`, `autosave`, `restore`, `original`, `external`, `saveAs` or `conflictCopy`. `file.versions={"delete":"document"}` deletes the open presentation's history and `{"delete":"all"}` every presentation's, in every history folder; Preferences › Saving has buttons for both, each with a confirmation. `file.versions={"open":"id"}` answers with the version's record and bytes and changes nothing in the session. `file.versions={"restore":"id"}` replaces the current content in one Undo step. Unsaved changes are first stored as an `autosave` version, so the state before the restore stays in the history, and the restored bytes are then recorded at once as a new `restore` version, whether or not AutoSave writes the file afterwards. Every command takes `document`, the uid of an open presentation, and acts on the active one by default. While a previous version is in front, they act on the history of the presentation it came from.

Each version's `details` records, as far as is useful and no further: the previous version (`parent`) and the origin of a copy; the UTC time with the local offset, the start of the editing session and how long it had run; what caused the save (`trigger`: `save`, `autosave`, `close`, `restore:<version>`, `saveAs`, `copy`, `beforeSave` or `beforeRestore`); the author's name and initials; a random installation id made once and kept in the settings folder, and a device label the user can edit (by default only the system name, "Windows" or "Mac"), with the operating system and the DeckCraft version and commit; the path relative to the provider's folder or the user's folder, with any folder named after the account replaced by `<user>`, and the provider; the size, modification time and SHA-256 of what was on disk before the save; the title, creator, last modified by and revision from `docProps/core.xml`; and counts of slides, shapes, pictures, media, comments and notes pages. No text of the presentation goes into the records, only counts and hashes. No location, IP address or keystrokes are recorded. The host name and account name are never recorded.

### The Version History pane and previous versions

File › Info › Version History opens the right-hand history pane. Clicking the presentation's name in the title bar (left or right button) opens a small file menu, as PowerPoint does for a OneDrive file: the file name, which can be changed there and applied with Enter (`file.rename`: the file is renamed in its folder, the extension is kept, a name already taken or one a file system cannot hold is refused, and the history and the AutoSave choice follow it); the folder that holds the file, or Not saved; and Version History.

The pane lists versions newest first under day headings: Today, Yesterday, or the date (month names in English and Portuguese, an ISO date in other interface languages). Each row shows the local time and the author, with an Open version link; hovering a row shows its full date and time, and right-clicking it offers Open version and Restore. With no versions the pane says why: the presentation has not been saved yet, the history is empty, or (in the browser) the history is kept by the desktop app.

Before a version is opened or restored, AutoSave writes the current presentation if it has unsaved changes, so that state is in the history too. DeckCraft keeps several presentations open, so an opened version (`file.openVersion={"id":"..."}`) is shown as a separate, read only presentation beside the one it came from, not in its place; opening another version for the same presentation replaces the one shown. It has no file, so AutoSave has nothing to write for it, and its title bar reads `Name (version <local date time>) — Previous version`. Commands that would change it, including Undo and Redo, are refused with a status-line message, and so is a mouse gesture that would move, resize or draw; file commands, the view, moving through the slides, selecting and copying still work. Its row in the pane is highlighted and has no link. A Previous version bar below the ribbon shows the date, time and author with **Compare**, **Restore**, **Save a copy** and **Close**.

- **Compare** (`file.compareVersion={}`) uses the deck comparison of Review › Compare with the previous version as the original and the presentation it came from as the revised one. The slide-level differences are listed in the Revisions pane, which for a version offers no Accept or Reject. Pressing Compare again shows the version and brings back the history pane.
- **Restore** first returns to the presentation the version came from, then runs `file.versions={"restore":"id"}`: the version becomes the presentation's content in one Undo step and is recorded at once as a `restore` version.
- **Save a copy** saves the version as a new file with the system Save dialog (`file.saveAs`, whose answer then carries `copyOf`). The copy gets an id of its own and records its origin; the window then goes back to the presentation it came from.
- **Close** (`file.closeVersion={}`, or File › Close) closes the version. The presentation it came from was never touched, so it is exactly as it was: its unsaved changes, undo history, selection and AutoSave stamp.

New, Open and quitting while a version is shown first close the version, so the presentation it came from is in front again; Close stops there, and New, Open or Quit then save or ask about the presentation's changes as usual. Closing the presentation a version came from closes the version too.

## Limits

The feature depends on a compatible sync client being installed and signed in. There is no cloud API, server-side merge or real-time coauthoring. The version history described above is kept in the desktop profile, or in the folders chosen in Preferences, is not synchronized by DeckCraft itself (a folder a sync app keeps is), and is unavailable in the browser. iCloud Drive, Google Drive and OneDrive keep their own server-side histories; DeckCraft does not browse or merge those histories.
